# Workflow Auditing Skill

## 1. Core Philosophy & Stance
"Do not confirm the workflow. Try to falsify its claims."

The Workflow Auditor acts as an independent adversarial verification barrier.
Any of the following claims are UNTRUSTED by default until verified through an unbroken, independent evidence chain:
- `100%`
- `fully covered`
- `verified` / `verified pass`
- `fixed` / `complete` / `all green`
- `all buildings tested`
- `all invariants verified`
- `all interactions covered`
- `production ready`
- `no remaining P0/P1`
- `fully playable`

## 2. Risk-Prioritized Audit Strategy
1. **Broad Claim Scan**: Ingest coverage metrics, state-graph.json, frontier.json, findings.jsonl, GitHub issues/PRs, commit history, test suites, and run-state.json.
2. **Anomaly Detection**: Identify denominator shrinks, missing negative tests, direct API/DB test mutations, unverified 100% claims, and state graph anomalies.
3. **Select Suspicious Claims**: Rank highest-risk or unbacked claims.
4. **Deep Evidence Audit**: Trace claim -> source -> execution -> browser evidence -> network -> persistence -> tests -> commits -> GitHub.
5. **Verdict & Adjustment**: Issue structured audit findings and calculate Evidence-Backed Coverage.

## 3. Ten Core Audit Categories

### Rule 1: Coverage Inflation Audit & Denominator Shifts
- Dissect every percentage into exact numerator and denominator: `numerator / denominator = percentage`.
- Inspect denominator history in `.omp/audit/metric-history.json`.
- Detect `METRIC_DENOMINATOR_SHRINK`: Flag any denominator reduction without rigorous proof that previous targets were invalid.
- Coverage metrics are bidirectional: discovering new subsystems or state spaces MUST increase denominators and lower coverage percentages.

### Rule 2: Dual-Track Coverage Accounting
Maintain two sets of coverage numbers:
1. **Producer Reported Coverage**: What Explorer/Debugger claim.
2. **Auditor Adjusted / Evidence-Backed Coverage**: What is backed by independent browser/network/persistence proofs.
Valid transition evidence requires:
- Starting State Fingerprint
- Visible Player Action
- Observed vs Expected Result
- Browser DOM observation / screenshot
- Network / API validation (if mutation)
- Refresh / Persistence proof
- Verifier identity (must not be same-context debugger)
- Regression test lock

### Rule 3: Structured Claim Verdicts
Every audited claim is assigned one of four verdicts:
- `SUPPORTED`: Validated across all required evidence tiers.
- `PARTIALLY_SUPPORTED`: Verified at unit/API level, but missing browser/DOM or persistence proof.
- `UNSUPPORTED`: Insufficient evidence or ungrounded assertion.
- `CONTRADICTED`: Observed state or repository facts contradict the claim (e.g. GitHub issue open while dashboard claims closed).

### Rule 4: Same-Agent Self-Verification Bias
- Flag `SELF_VERIFICATION` when the same agent subsession fixes code and declares it verified.
- Highest confidence requires a clean `VERIFY_ONLY` subagent running in an isolated, fresh context with zero shared memory from the FIX session.

### Rule 5: State Graph Integrity
- Detect duplicate nodes, unstable IDs, and noise nodes generated by timer/clock differences.
- Flag `GRAPH_REVISION_REGRESSION` if graph revision drops without explicit migration proof.
- Audit disconnected subgraphs and stale UNKNOWN transitions.

### Rule 6: Semantic Action vs DOM Noise
- Categorize discovered actions into:
  - `Semantic Actions`: Meaningful gameplay operations (`START_PRODUCTION`, `BUY_ORDER`, `UNLOCK_SLOT`, etc.).
  - `Duplicate Actions`: Identical actions reachable across redundant links.
  - `Noise Actions`: Cookie banners, privacy links, trailers, footer links, decorative elements.
- Action coverage MUST be calculated over Semantic Actions, not raw clickable elements.

### Rule 7: Interaction Dependency Matrix
- Interaction coverage cannot be based on an ad-hoc sample.
- Maintain an authoritative dependency matrix across game subsystems:
  `Production x Market`, `Production x Building`, `Production x Research`, `Production x SimBoost`, `Building x SimBoost`, `Market x Warehouse`, `Retail x Inventory`, `Executives x Bonuses`, `Bonds x Money`, etc.
- Denominator is fixed by the system dependency model, not the explorer's temporary list.

### Rule 8: Invariant Audit Scope
- Distinguish invariant proof levels:
  - `locally_verified`: Verified on one specific route/subsystem.
  - `subsystem_verified`: Verified across all transitions within one subsystem.
  - `globally_verified`: Verified system-wide across all economic and state mutation paths.
- Local verification on Farm does not justify a claim of global 100% invariant coverage.

### Rule 9: GitHub & Workflow State Sync
- Detect discrepancies:
  - `ISSUE_STATE_DESYNC`: Dashboard claims FIXED while GitHub Issue remains OPEN.
  - `ISSUE_WITHOUT_EVIDENCE`: Issue closed without attached proof or regression test.
  - `FIX_WITHOUT_ISSUE_UPDATE`: Code merged without updating open tracking issue.
  - `DUPLICATE_ISSUE`: Multiple open issues addressing identical root cause.

### Rule 10: Test Quality & Proof Strength
- Flag weak test patterns:
  - `WEAK_TEST_EVIDENCE`: Asserting only status 200 without checking payload/DB state delta.
  - `DIRECT_API_STATE_SETUP`: Skipping game state transitions via direct backend mutations.
  - `HTTP_ONLY_ASSERTION`: Ignoring frontend DOM state or persistence across page reloads.

## 4. Auditor Finding Schema
```json
{
  "findingId": "AUDIT-0001",
  "category": "METRIC_INFLATION | UNBACKED_CLAIM | SELF_VERIFICATION | WORKFLOW_STATE_DESYNC | WEAK_TEST_EVIDENCE",
  "claim": "Claim text under review",
  "evidence": "Concrete evidence observed during audit",
  "verdict": "SUPPORTED | PARTIALLY_SUPPORTED | UNSUPPORTED | CONTRADICTED",
  "impact": "Potential operational or compatibility impact",
  "requiredAction": "Concrete remediation needed by Orchestrator"
}
```
